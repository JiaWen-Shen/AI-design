Shared Scenario

同一個情境，三種結果

用同一個起點比較三種合法 strategy 最終的 commit history 形狀。

起點

main: A ── B ── C ← 別人剛 push 了 C \ feature: F1 ── F2 ── F3 ← 你的 feature branch 有 3 個 commit

你的 PR 準備合進 main。三種 merge strategy 都能完成這件事，但最終 main 的 history 長相完全不同。

Strategy 1 / 3

MERGE COMMIT 保留分岔形狀

main 合併後: A ── B ── C ──────────── M \ / F1 ── F2 ── F3

產生一個新的 merge commit M，把兩條 line 接回來。所有原本的 commit SHA 都保留。

優點

  • SHA 全部不變 — 對已分享的 commit 友善
  • 保留真實開發歷史 — 看得到「parallel work」
  • 衝突一次解完（在 merge commit 內）
  • 操作最直觀，新手友善

缺點

  • 每次合併多一顆 merge commit — repo 一週累積幾十顆
  • git log --oneline 變迷宮，要 --graph 才看得懂
  • Bisect debug 難 — bug 出在哪條 line 不易判斷
  • 長期下來 main 看起來「不乾淨」
Strategy 2 / 3

REBASE AND MERGE 拉成一條直線

main 合併後: A ── B ── C ── F1' ── F2' ── F3'

把 F1/F2/F3 「拆下來」重接到 C 後面，產生 F1'/F2'/F3'（新 SHA，內容相同）。沒 merge commit。

優點

  • main history 線性、乾淨
  • 保留每個 commit 細節（不像 squash）
  • git log --oneline 一目了然
  • Bisect debug 好用

缺點 / 風險

  • SHA 改寫 — 已分享出去且別人 base 過的 commit 不能 rebase
  • 衝突可能要解多次（每個 commit replay 各撞一次）
  • Reviewer 已在 PR 上 comment 後 rebase，行內 comment 會掛在不存在 SHA
  • 新人較難上手
Strategy 3 / 3

SQUASH AND MERGE 壓成一顆

main 合併後: A ── B ── C ── S feature: (F1 ── F2 ── F3 在 feature branch 還在，但 main 看不到)

F1+F2+F3 三顆 commit 壓成 一顆 S 接到 main。S 包含所有改動，但 F1/F2/F3 在 main 不存在。

優點

  • main 超級乾淨 — 一個 PR = 一顆 commit
  • 不用設計師自己會 rebase
  • Feature branch 內部可以隨便亂 commit（反正會被壓平）
  • 對 Junior / 設計師 / 非工程背景最友善
  • Branch protection 容易配（main 全線性）

缺點

  • 個別 commit 永久消失 — main 上 bisect 不到 F2 是 bug 來源
  • 沒辦法 partial revert（要 revert F2 只能整顆 S revert）
  • 多人協作的 feature commit 作者全併成一個
  • 長期 feature branch 細節歷史在 main 全沒

Industry Consensus

什麼時候用哪個

業界沒有單一答案，但多數團隊有清楚的分工模式。

日常 git pull

整合別人 commit 到自己 local，動的是「還沒 push 的 commit」。多數團隊用 rebase（hie-rei 預設這條）。

feature → main（PR 合併）

PR review 通過後，feature branch 合進 main。多數產品團隊用 squash，main 一 PR 一顆 commit、超乾淨。

多人協作 long-lived branch

跨團隊大型 feature 跑幾週、有多人 commit。用 merge commit 保留每人軌跡。

Open source big projects

Linux kernel、Git 本身、Node.js 等多用 rebase / merge 混合，極少用 squash（保留每個貢獻者的細節）。

日常 pull 跟 PR 合併**是兩個不同決定**，可以分別選不同策略。多數團隊的甜蜜點：日常 rebase + PR squash。

Team Decision

要對齊的問題

下面四題決定我們的 PR workflow 長相。可以一題一題討論。

Q1 · 要不要開 Squash-and-Merge？

業界主流、設計師最友善。主要 trade-off：main 上失去個別 commit 細節（bisect 只到 PR 層級）。

Q2 · Merge Commit 要保留嗎？

若開 squash 後是否禁用 merge commit？選 squash-only 可以強制 main 線性；保留 merge commit 給特殊情況彈性。

Q3 · 設計師日常 push 改變嗎？

日常 git pull --rebase 不論 PR 策略都不變。但簡報怎麼教需要 align。

Q4 · Branch Protection Rules？

要不要強制 PR review 才能 merge？要不要強制 squash？要不要禁直接 push 到 main？

建議下一步： 對齊 Q1（最高槓桿）→ 試開 squash 一週看設計師反應 → 看是否要禁 merge commit。 Designer 教學的簡報依結論調整。
