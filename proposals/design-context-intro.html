Part 2 · A new skill proposal · v0.1

Design Response
to Requirements.

design-context — a Claude Code skill that loads department rules and project specs into your AI context, so your designs respond to what's actually written, and judgement stays in your hands.

The rest of the deck walks the proposal: Problem → Solution → How it works → Worked example (Q1-1 Teen Onboarding, v1 vs v2 mockups) → Designer judgement → Setup → Tactical feedback.

Problem

Two friction points in every design session

It's not that design is hard. It's that context is hard to retrieve.

Pain 1

The design system isn't where your AI looks

TLDS tokens, brand voice, and component specs all live in trendlife-general/vxd-skill. Your agent doesn't read them automatically. Every session, you re-paste the rules or re-explain the tokens.

  • The agent invents hex values and spacing on the fly
  • Rule updates never reach designers in time
  • "Follow TLDS" turns into a slogan instead of a check
Pain 2

PM specs move faster than you can track

REI-Project/docs/requirements/ gets several commits a day. In the past week alone, Catherine and Heather pushed dozens of edits. You may be designing against a spec that quietly changed an hour ago.

  • The agent reasons from yesterday's spec
  • Designs finish after requirements have moved on
  • Cross-timezone gaps make this worse

Today's workaround: paste the spec at the start of each session, remind the agent about tokens, hope nothing was missed. Repetitive, error-prone — and the agent still improvises.

Solution

What design-context does — three things

Auto-sync L1 — department rules and L2 — project specs

A background cron pulls every 30 minutes, with a SessionStart hook as a backup. L1 is machine-global (~/.cache/), L2 is per-project (.design-context/, gitignored — never leaks into your repo).

Force the agent to read the right files on activation

SKILL.md uses an On Activation pattern — when you say "follow TLDS" or "design from Q1-1", the skill triggers and the agent must read the listed tokens and spec before responding. No reading, no answer.

Surface spec changes proactively

When a sync catches changes above threshold (> 2 files or > 50 lines), macOS notifies you in real time. An update digest (diff + author + commit message) is written to the cache; the next time you trigger the skill, the agent reads it and tells you "Q15 changed three times since your last session — likely affects this flow."

Zero designer overhead — run init.sh once, then forget the skill is there.

L1 — department

vxd-skill

Plain shallow clone What it means: Clone only the latest version — skip every past commit's history.

Why: Designers need the current token values, not a record of how they were 6 months ago. Smaller download, fast. vxd-skill: 27 MB full → 3.5 MB shallow into ~/.cache/design-context/vxd-skill/. 3.5 MB, shared across every project. TTL: weekly.

Contents: TLDS tokens, brand, motion specs, component specs.

L2 — project

REI-Project specs

Sparse-checkout What it means: Download the repo's full structure, but only write the folders you ask for to disk.

Why: REI-Project carries RD source code, infra configs, and other team assets that designers never look at. Sparse skips them entirely. REI-Project: 171 MB full → 25 MB sparse
(docs/ + teams/PM only) into <cwd>/.design-context/. 25 MB total — avoiding the full 171 MB repo. TTL: SessionStart + every 30 min.

Contents: docs/requirements, docs/project, docs/design, docs/ui, teams/PM.

Want to edit a rule? Don't touch the cache. Open a branch and PR in the source repo (Type A workflow). The cache is a read-only copy — it gets overwritten on every sync.

Important

The skill doesn't replace design judgement

It brings the rules and the spec to the table. You still decide what to do with them.

What the skill does
  • Surfaces the raw spec and tokens into the agent's context
  • Reminds you that "Q15 changed three times since last session"
  • Stops the agent from inventing colors and spacing
  • Makes the agent cite token names instead of hex values
What you still do
  • Read the spec and ask "is this actually right?"
  • Spot contradictions within the spec itself
  • Use design knowledge to restructure the proposal
  • Push back to PM — with the trade-offs on record

v2 is the concrete proof of this principle

Q1-1's spec contradicts itself in four places (its own design principles versus its option list). The designer chose to push back — citing the spec text and HIE's internal design doc as evidence for every cut. The skill doesn't make that judgement for you — but because both the spec and the doc are loaded into context, the judgement is cheaper to make.

Setup

Set up once. Forget it exists.

First time: run init.sh

bash ~/Jottacloud/vibe/AI-design/design-context/scripts/init.sh
Interactive setup — pick the sources to track (defaults: vxd-skill + REI PM specs), install the launchd cron job, and register the SessionStart hook into your project's .claude/settings.json.

Day to day: just use a trigger phrase

English: design from Q1-1 · design status · design refresh · follow TLDS
Chinese: 「請根據 Q1-1 做設計」·「用部門規範」·「依照 TLDS」·「context 還新嗎」
Natural-language matching is handled by SKILL.md — you don't memorise commands.

When specs change — the notification finds you

No manual refresh. When the cron picks up changes above threshold, macOS notifies you; the next time you talk to the agent, a diff summary is included inline so you immediately know what moved.

Distribution path

Currently lives in AI-design/design-context/ as personal development. After this feedback round and iteration, it ships to REI-Project/.claude/skills/design-context/ via a normal PR review — and the whole design team picks it up automatically.

Feedback

Four questions for you

This is v0.1. Your reactions decide where it goes next.

1. Do the trigger phrases feel natural?
"design from Q1-1" / "follow TLDS" / "請根據 Q1-1 做設計" — would you actually say these in a session? If a different phrasing feels more intuitive, we can add it as an alias.
2. Are the notifications going to be too noisy?
Current threshold: more than 2 files or 50 lines triggers a macOS notification. PMs may push multiple times a day. Would you prefer instant alerts, a once-a-day digest, or notifications only when you're actively working on the spec that changed?
3. Which folders should L2 pull in?
Currently sparse-checked-out: docs/requirements/, docs/project/, docs/design/, docs/ui/, teams/PM/. Anything to add or drop? Should resources/design/ (Figma sources) be in scope?
4. Is the v2-notes "design rationale" format useful?
Each deviation from the spec carries why / trade-off / open question for PM. Is this format helpful for PM review — or too verbose? Should we turn it into a template?
