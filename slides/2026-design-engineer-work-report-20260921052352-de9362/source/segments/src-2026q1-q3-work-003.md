# 一、Bridge Designers ↔ AI workflow

## 一、Bridge Designers ↔ AI workflow ### 1. 設計師 AI / Git 協作內訓與教材系統 **Duration：** 2026/04–2026/08 **題目：** 從 Git 與 repository 基礎，到 Claude Code、模型設定與跨裝置協作的設計師 AI 工作方法。 **大綱：** - 建立 GitHub for UI Designers 系列：Git 與 Figma 的對照、branch / fork、remote / local、PR review、衝突處理與安全復原。 - 製作 Claude Design / Claude Code 分享，釐清 Desktop、CLI 與設計師 handoff 的使用邊界，並納入 anti-AI-slop 與現場 Q&A。 - 延伸成跨 repo 架構、design context、模型選擇與設定、VPN / 帳號遷移、1 小時 prompt cache 等可操作教材。 - 於 Demo Day 完成部署與內容調整，保留未完成驗證的誠實揭露。 **可量化資料：** AI-design 於 4–8 月記錄 **122 commits**；產出 Week 1–6 系列、31 頁 Claude Design 分享、雙語互動式模型設定指南與 Demo Day 簡報等教材。 ### 2. 設計師 AI 工作流工具：PR Review、Design Context 與 Repository 架構 **Duration：** 2026/04–2026/06（後續持續維運） **題目：** 讓設計師能安全地在 repository 內使用 AI、取得正確 context，並自行檢查設計交付。 **大綱：** - 提出 Designer Multi-Layer Repository Architecture，整理工作 repo、reference repo 與跨團隊協作的分層方式。 - 建立 `design-pr-review`：將設計 PR render 成可比較的畫面，檢查 before / after、CSS 規範與 design token 使用。 - 建立 `design-context`：將部門規範與 PM 規格以 shallow clone、sparse checkout 與 session hook 分層同步至設計師工作環境。 - 完成 Preview Hub / mockup upload POC、designer setup guide、跨 repo template 與交接流程，降低設計師進入 Git / AI 工作流的門檻。 **可量化資料：** `design-pr-review` 在 5 月經 **5 輪 adversarial review**、**40/40 e2e** 驗證後完成半自動 merge 衝突分流；`design-context` 以 L1 部門規範與 L2 專案規格兩層同步，避免將完整大型 reference repo 複製到每個工作目錄。 ### 3. AI 開發環境、存取管理與跨 Runtime 相容 **Duration：** 2026/06–2026/09 **題目：** 將 AI 模型、帳號、憑證與多工具環境，包裝成設計團隊可安全採用的入口與運作規則。 **大綱：** - 交付 1 小時 prompt cache 設定包：安裝、驗證、雙語說明與回報機制，降低長 context 的使用成本。 - 完成公司 AI 存取管理 plugin：整合 credential、model switching、access gate、跨平台 launcher 與 reset / recovery 流程。 - 建立 Claude Code × Codex CLI 指令共用層：以 `AGENTS.md` 為共同契約、完成 canary 驗證與每日安全同步。 - 修正 profile 模式下個人 skills 無法被載入的問題，讓不同 profile 仍可發現並使用必要工具。 **可量化資料：** AI 存取管理 plugin 於 8 月完成 **116 commits、20+ PR**、版本 **0.3 → 0.13**，含 bash 與 PowerShell 兩套 launcher、9 組 regression；跨 Runtime 相容計畫已對 **22 個專案**產生 `AGENTS.md`，其中 **20 個**完成乾淨 push。 ### 4. AIUX 協作治理、健康檢查與日常作業流程 **Duration：** 2026/04–2026/09 **題目：** 將 AIUX 團隊的需求、上下文、交接與健康狀態，轉成可追蹤、可重複執行的工具與規則。 **大綱：** - 先後建立 Teams / Outlook 需求彙整、UXD weekly digest 與新進人員 onboarding 的基礎工具。 - 建立 AI environment healthcheck：讓訪談者與受訪者各自運行可攜工具，再以逐字稿與機械檢測交叉分析。 - 建立 squad sync、daily summary、checkpoint、remote-first sync 與 handoff 機制，將日常交接轉成有 scope gate 與 regression 的流程。 - 執行 context bloat diet，量測並降低每次 agent session 的固定 context 開銷。 **可量化資料：** healthcheck 在 7 月完成 **8 場訪談、18 份機械檢測資料**並彙整為三層問題分類；context bloat diet 實測降低 memory-file 開銷 **36%**、skill-description 開銷 **44%**。 ### 5. Open Design 平台評估與 TLDS 設計系統 Pipeline **Duration：** 2026/08–至今 **題目：** 評估並建立可讓設計團隊與 MKT 使用的 AI design platform、設計系統與 deck 產出路徑。 **大綱：** - 建立本機 Open Design CLI workflow 與專案級 token / deliverable ledger。 - 比較 Open Design、Figma AI / Make、Claude `/design`、Canva、Google Stitch、Lovart 等平台，以 UX、協作、GitHub / OneDrive、設計系統約束、成本與輸出品質建立 evidence-graded matrix。 - 將候選收斂到 Open Design 與 Figma AI / Make，並提出公司級 self-host 方案：pilot → wave → full rollout、per-user daemon pod、權限隔離與 code-first handoff。 - 將 TLDS package、設計 token、素材資產與 deck verifier 接入 Open Design pipeline，持續處理產出品質與 pipeline 強制性問題。 **可量化資料：** 8/31 建立首份 Open Design ledger，辨識 **91 個 session、7,743 個 usage events**；9 月完成 **6 家平台 matrix**與對外可讀 HTML 報告，並將 TLDS package 整理為 **64 個檔案**的可掛載設計系統快照。 ---
